## 0. 원칙 — 태그로 태어나기

- 기계가 만드는 기록(장면 기록·기계 신호·상태)은 한국어 산문으로 번역해 보내지 않고, **처음부터 넥서스 언어 태그 캡슐로 태어나게** 한다. 변환 프로그램을 따로 만들어 글로 쓴 뒤 번역하지 않는다 — 구조화된 원천에서 곧장 캡슐로 찍어 낸다.
- 사람의 대화·프로젝트 책임자 말씀은 압축 대상이 아니다. 캡슐 안에 들어갈 때도 문법 정본 §6 보호 구역으로, 따옴표 원문 그대로 둔다.
- 압축 언어 적용은 읽는 두뇌의 능력으로 가른다 (§5 독자 조건). 작은 두뇌의 에코 결함 실측(2026-11-04)이 그 근거다.

## 1. 캡슐 문법 — 사건 9칸을 한 줄로

### 1.1 장부 머리 (장부당 1회 — 공유 상태)

캡슐은 L1 사건 장부 안에 산다. 날짜·시간대·장부 주인은 사건마다 다시 싣지 않고 장부 머리가 한 번만 선언한다. 이것이 이 문법의 절감 본체다 — 문법 정본 §11·§12의 "공유된 상태는 다시 싣지 않는다"를 장부에 적용한 꼴이며, §4 실측에서 v1(자기완결형)과 v2(장부 공유형)의 차이가 이를 증명한다.

```
@NL 1.0
DICT 사전_v1@1.2+제안
LEDGER @R/20260115 TZ +0900 OWNER 프로젝트 책임자
---
<캡슐 줄들 — 한 줄 = 한 사건>
```

- `LEDGER` 값: 장부의 루트 주소(`@R/<YYYYMMDD>`) · 시간대 오프셋 · 장부 주인. 캡슐의 주소·시각·자리는 이 머리를 기준으로 복원된다.
- 장부를 전문(메시지)으로 내보낼 때는 문법 정본 §1 꼴(`@NL` 머리 + `#H=` 해시)로 감싼다. 장부 자체의 무결성은 일별 마감 해시 1회로 확인한다.

### 1.2 캡슐 꼴 — 순서 고정

```
EV=<일련> TM=<시각> PL=<자리> KD=<종류> CT=<내용> [XY=<좌표>] [RF=<근거>] [SV=<민감도>] [LK=<연결>]
```

- 한 줄 = 한 사건. 필드는 공백 하나로 구분하고, 순서는 위 고정 순서를 지킨다 (문법 정본 §2-5: 순서가 의미를 갖는 경우 줄 순서가 곧 순서 — 캡슐 안 필드 순서도 같은 원리).
- 값 안에 공백을 두지 않는다. 공백이 필요한 사람말 원문은 `"…"`로 감싼다 (보호 구역 — 압축·치환 대상 아님, 문법 정본 §2-4·§6).
- 값 안 구분자: 계층·조각 연결 `/` · 이름-값 쌍 `이름:값` · 목록 나열 `,`.

### 1.3 필드 정의 — 규격 9칸과의 대응

| 순서 | 태그 | 대응 칸 | 필수/선택 | 값 규칙 |
|---|---|---|---|---|
| 1 | `EV` | 1. 주소 | 필수 | 장부 안 일련 4자리. 복원 시 장부 머리의 `@R/<일자>/`를 앞에 붙인다. 장부 밖을 가리킬 때만 전체 주소 `@R/20260115/0037` 꼴 |
| 2 | `TM` | 2. 시각 | 필수 | `HHMM` (필요 시 `HHMMSS`). 날짜와 시간대는 장부 머리가 공유한다 |
| 3 | `PL` | 3. 자리 (+1칸의 계층 주소 병기 흡수) | 필수 | 계층 경로를 `/`로 잇는다: `누구/기기/앱·화면/위치`. 첫 칸이 장부 OWNER와 같으면 생략하고 기기부터 쓴다 |
| 4 | `KD` | 4. 종류 | 필수 | 값 코드표(§1.4) 중 하나 |
| 5 | `CT` | 5. 내용 | 필수 | `대상/행동/결과`를 `/`로 잇는다. 결과 조각이 없으면 둘까지만. 사람말 원문 조각은 `"…"` 인용 |
| 6 | `XY` | 6. 좌표 | 선택 | 채널별 수치·태그 목록. 화면=요소 상태 쌍, 장면=장면 태그, 음성=`len:<초>s`, 기기=전/후 상태 쌍 등 `이름:값` 나열 |
| 7 | `RF` | 7. 근거 | 선택 | 증거 층(L3) 주소. 장부 일자 기준 상대 경로를 기본으로 한다(예: `캡처/0037`). **없으면 필드 자체를 생략**한다 (생략 = 근거 없음) |
| 8 | `SV` | 8. 민감도 | 선택 | `1` = 민감(요약만 남김). **일반(0)이면 생략**한다 (생략 = 일반). `2` 제외는 캡슐을 만들지 않는다는 규칙이라 값으로 존재하지 않는다 |
| 9 | `LK` | 9. 연결 | 선택 | 얽힌 사건·덩어리의 주소 목록(`,` 나열). 같은 장부 안 사건은 일련만, 밖의 주소(타일 등)는 전체 주소 |

규격 초안의 주소 칸에 있던 "아카식 계층 주소 병기(기기>앱>화면)"는 자리(PL)와 내용이 겹쳐 PL로 흡수했다. 구분자는 아카식 주소의 `/`로 통일한다 (문법 정본 §15 FRC — 어느 층에서 봐도 주소의 꼴은 같다).

### 1.4 값 코드

종류 `KD` (규격 초안의 7종과 1:1):

| 코드 | 종류 | 코드 | 종류 |
|---|---|---|---|
| `SC` | 화면 | `CM` | 명령 |
| `AU` | 음성 | `DV` | 기기 |
| `VS` | 장면 | `SY` | 시스템 |
| `TC` | 터치 | | |

민감도 `SV`: 생략 = 일반 · `1` = 민감 · (제외는 기록 자체를 만들지 않음 — 규격 초안 §5-4)

### 1.5 신규 태그 등록 제안 (사전 정본은 수정하지 않음)

아래 9개는 사전 v1.2에 없는 신규 태그의 **등록 제안**이다. 등록 조건(문법 정본 §7-3)의 왕복 복원 검사는 §2의 예시 3건이 1차 증거이며, 정식 등록 시 사전 minor 판본 상승(1.2 → 1.3)과 함께 처리한다.

| 태그 | 층 | 원문 | 용법 |
|---|---|---|---|
| `EV` | 지시 | 사건 캡슐 | L1 장부에서 사건 한 줄을 여는 표지. 값은 사건 주소(장부 안에서는 일련) |
| `TM` | 데이터 | 시각 | 값 꼴 `HHMM`/`HHMMSS`. 날짜·시간대는 장부 머리가 공유 |
| `PL` | 데이터 | 자리 | 계층 경로. 첫 칸 기본값은 장부 OWNER |
| `KD` | 데이터 | 종류 | 값은 §1.4 코드표 |
| `CT` | 데이터 | 내용 | 대상/행동/결과 조각. 사람말은 따옴표 보호 구역 |
| `XY` | 데이터 | 좌표 | 채널별 수치·태그 목록 |
| `RF` | 데이터 | 근거 | 증거 층 주소. 없으면 생략 |
| `SV` | 데이터 | 민감도 | 생략 = 일반, `1` = 민감 |
| `LK` | 데이터 | 연결 | 얽힌 주소 목록 (§14 얽힘 집합의 주소 나열과 같은 꼴) |

충돌 검사: 사전 v1.2 등록 19항목(`PV`·`[계산]`·`[창고]`·`[언어]`·`T`·`[µ사전]`·`금지`·`%`·`H`·`Q`·`D`·`U`·`A`·`L`·`→`·`@`·`RT`·`JD`·`Δ`)과 문법 전문 머리 키(`DICT`·`SID`·`LAYER`·`MAP`) 전부와 대조 — 제안 9개와 겹치는 이름은 없다. 기존 태그 재사용 지점: 주소 참조는 기존 `@`, 얽힘 연결의 의미는 §14를 그대로 따른다 (새 의미를 만들지 않았다).

## 2. 예시와 왕복 복원 (§7-3 등록 조건의 1차 증거)

복원문은 캡슐 + 사전 제안 + 장부 머리만으로 되읽은 규격 한 줄이다. 세 예시 모두 9칸 전부가 복원됨을 대조했다.

### 예시 1 — 브라우저 화면 (합성 예시)

- 산문형: "2026년 1월 15일 오전 10시 20분, 프로젝트 책임자의 전화기 브라우저에 예시 포털의 로그인 화면이 준비되었다. 서비스 이름이 표시되어 있고 사용자 이름 칸과 비밀번호 칸은 비어 있었다. 캡처가 근거로 남았고, 다음 사건과 연결된다."
- 태그형:
```
EV=0037 TM=1020 PL=전화기/브라우저/포털로그인 KD=SC CT=로그인화면/준비완료/서비스명표시 XY=사용자칸:빈값,비밀번호칸:빈값 RF=캡처/0037 LK=0038
```
- 복원: `REC-20260115-0037 | 2026-01-15 10:20 | 프로젝트 책임자>전화기>브라우저>포털로그인 | 화면 | 로그인 화면 준비 완료 — 서비스명 표시 | 요소: 사용자칸 빈값, 비밀번호칸 빈값 | 근거: 캡처/2026-01-15/0037 | 일반 | 연결: REC-20260115-0038` — 9칸 전부 복원 ✓

### 예시 2 — 장면 기록 (민감)

- 산문형: "2026년 1월 15일 오후 3시 40분, 프로젝트 책임자의 전화기 카메라가 현관을 기록했다. 실내 현관에서 택배 상자 한 개가 문 앞에 놓여 있었고 조명은 꺼져 있었다. 사진 원본은 폐기되고 기록만 남았으며 민감 등급이다."
- 태그형:
```
EV=0102 TM=1540 PL=전화기/카메라/현관 KD=VS CT=현관장면/기록/택배상자1개문앞,조명꺼짐 XY=실내,상자:1,조명:off SV=1
```
- 복원: `REC-20260115-0102 | 2026-01-15 15:40 | 프로젝트 책임자>전화기>카메라>현관 | 장면 | 현관 장면 기록 — 택배 상자 1개 문 앞, 조명 꺼짐 | 실내, 상자 1, 조명 off | 근거: 없음(원본 폐기) | 민감 | 연결: 없음` — 9칸 전부 복원 ✓ (RF 생략 = 근거 없음으로 복원됨)

### 예시 3 — 음성 명령 (사람말 보호 구역)

- 산문형: "2026년 1월 15일 오후 7시 5분, 프로젝트 책임자가 전화기 마이크로 2.4초간 말했다. 핵심 전사는 에어컨을 켜라는 명령이었고, 세션 안에서만 처리되어 원본은 남지 않았다."
- 태그형:
```
EV=0145 TM=1905 PL=전화기/마이크 KD=AU CT=음성명령/수신/"에어컨 켜 줘" XY=len:2.4s
```
- 복원: `REC-20260115-0145 | 2026-01-15 19:05 | 프로젝트 책임자>전화기>마이크 | 음성 | 음성 명령 수신 — "에어컨 켜 줘"(원문) | 길이 2.4초 | 근거: 없음(세션 내 처리) | 일반 | 연결: 없음` — 9칸 전부 복원 ✓. 전사 원문 "에어컨 켜 줘"는 따옴표 안에서 압축·치환 없이 그대로다.

## 3. 절감 실측

### 3.1 방법

- 표본 10건: 입력 갈래별 양식 예시(S1–S10). 전문은 부록에 수록했다. **게시본 고지: 아래 토큰 실측은 내부에 보관한 원 표본으로 잰 값이다. 부록의 표본 서술은 개인정보와 내부 구성 보호를 위해 날짜·시각·장면·수치를 바꾼 합성 예시로 교체했으며, 문법 구조는 원 표본과 같다.**
- 산문형 기준선: 오늘 사람이 장부에 쓰는 방식의 한국어 문장 (같은 정보를 담은 문장. 근거·민감도·연결은 산문 관행상 기본값일 때 생략하기도 하며, 태그형도 같은 기본값은 생략으로 맞췄다 — §1.3).
- 토크나이저 2종 실측 (지어낸 추정치 아님):
  - **Qwen3 토크나이저** — Hugging Face `Qwen/Qwen3-4B` 공식 `tokenizer.json`을 받아 VM 로컬에서 계수. 실제 독자인 웨이터(Qwen3-4B)와 같은 토크나이저라 주 지표로 쓴다.
  - **tiktoken cl100k_base** (0.14.0) — 참고 지표.
- 문자 수도 병기한다. 장부 머리는 장부(하루)당 1회 비용이라 사건당 수치에서 빼고 별도로 상각을 밝힌다.

### 3.2 1차 시도 — 자기완결형(v1)은 실패했다

사건마다 전체 주소(`@R/20260115/0037`)·전체 시각(`20260115T1020+0900`)·전 필드 키를 다 싣는 자기완결형으로 먼저 쟀다.

- Qwen: 산문 863 → 태그 v1 **1,090토큰 (+26.3%, 오히려 길어짐)**
- cl100k: 산문 1,024 → 태그 v1 992토큰 (−3.1%)

원인: 날짜·주소·필드 이름 같은 고정비가 사건마다 반복되는데, 한국어 산문은 그 정보를 문장 안에 녹여 더 싸게 나른다. **줄 단위 태그화만으로는 절감이 나지 않는다**는 것이 1차 실측의 결론이며, 이 실패가 장부 공유형(v2)의 근거다.

### 3.3 2차 — 장부 공유형(v2, 이 문서의 문법) 실측

장부 머리 실측: 68자, Qwen 47토큰 (장부당 1회 — 하루 100건이면 사건당 +0.47토큰, 200건이면 +0.24토큰으로 상각).

|---|---|---|---|---|---|---|---|---|---|

### 3.4 해석 — 솔직한 결론

1. **줄 단위 절감의 현실선은 평균 16.2%다** (Qwen·표본 10건 합계). "100분의 1"은 물론 50~70%에도 닿지 않는다. 내용이 짧고 좌표·연결이 무거운 사건(S6)은 태그형이 더 길어질 수 있다 — 태그화를 순수 토큰만으로 강제할 구간은 아니다.
2. 절감이 가장 큰 곳은 정보 밀도가 낮은 정형 사건이다 (음성 수신 39.7%, 장면 26.7%). 기계 신호류는 13.1%로 의외로 낮다 — 산문도 숫자 나열은 이미 싸기 때문이다.
3. 태그형의 주된 이득은 토큰이 아니라 **판독 방식**이다: 캡슐은 코드가 결정적으로 파싱해 검색·집계·판정을 모델 해석 없이 수행한다. 산문 장부는 읽을 때마다 모델이 해석해야 하고, 그 해석 비용은 이 표의 입력 토큰 비교에 잡히지 않는다.
4. 더 큰 절감은 줄이 아니라 **맥락 동기화**에 있다: 두뇌가 장부 전체를 다시 읽지 않고 델타만 받는 구조(문법 정본 §12, 기존 실측 내용 이동률 0.70)가 본줄기이며, 캡슐 문법은 그 델타가 실릴 그릇이다. 이 순서를 뒤집지 않는다.
5. 한계: 표본 10건·양식 예시 중심이며 산문 기준선은 작성 문체에 의존한다. 실사용 장부가 쌓이면 같은 방법으로 재측정한다 (특히 반복되는 PL·KD의 체감 절감은 표본이 작아 아직 잡히지 않았다).
